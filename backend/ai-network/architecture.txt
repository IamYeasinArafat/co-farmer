Hydro Monitor: Agentic Backend Plan
Sep 24, 2026 · @Von
The big picture 
The system has two halves: a hardware backend that collects readings and carries out actions, and an agentic backend that turns those readings into plans.
flowchart LR
  S[Sensors] --> E[Edge devices<br/>several per farm]
  E --> M[Master node<br/>one per farm]
  M -- readings every 10 s --> A[Agentic backend]
  A -- plan --> M
  M --> X[Pumps, fans, valves]
• Hardware backend (hardware teammate): sensors, edge devices and the master node. A large farm needs several edge devices; the master collects from all of them, uploads the readings, and carries out the plans it receives.
• Agentic backend (this doc): receives the data over the internet, analyses it, and sends a plan back to the master.

Phase 1: initial setup
Setup runs once per farm: the agent controller proposes an agent network for that farm, and a person approves it before anything runs.
flowchart LR
  A[Team installs hardware<br/>and notes what went where] --> B[Farm profile +<br/>controller system prompt]
  B --> C[Controller proposes<br/>departments and agents]
  C --> D{Person approves?}
  D -- yes --> E[System starts running]
  D -- no --> C
Each proposed agent is a small model with its own system prompt, created only for sensors the farm actually has: a farm without a methane sensor gets no methane agent. The point of this step is that every farm is different, so the network adapts to each one instead of being hard-coded.
Phase 2: the departments
Three departments do the work: the crop department plans, the agro-environment department sets ideal ranges, and Insight builds the dashboard. Each department has a manager agent that hands work to its worker agents.

How it fits with the earlier design
Agents plan and set the ranges; code watches the readings and enforces them.
• The agro-environment department sets each crop's ranges once, filling the role of the fixed safe ranges in the earlier design notes.
• Code checks every 10-second reading against those ranges and raises alerts, so no agent has to read the raw stream.
• The controller reads only the farm profile, which keeps each model call small and cheap.
This settles the earlier Python-vs-AI question: both are used, each for the job it does best.
Four things to settle before building
The meeting left four questions open, and the first two change what gets built.
1. Hydroponic or soil for the demo? Asked in the meeting, never answered. It decides the sensors (EC and water temperature vs. soil moisture) and whether a soil department exists at all.
2. Who builds the agent network? The framework won't design it. In CrewAI, each agent is a definition you write: role, goal, backstory and model, one JSON file per agent in new projects. Its hierarchical mode adds a manager agent that delegates tasks and checks results (CrewAI docs). So the controller's job is concrete: one model call that writes those agent files from the farm profile, then a person approves them. CrewAI is open source (MIT) and runs local models through Ollama (CrewAI on GitHub).
3. What happens while it runs? The recording cuts off at the data analyst. Still to decide: how often each department re-runs, what triggers a re-run, and what the plan sent to the master looks like.
4. The fine-tuning claim. The meeting suggested telling judges the models are fine-tuned. They won't be, and one question ("what data did you fine-tune on?") breaks the pitch. Say instead: specialised through system prompts, with fine-tuning planned once real harvest data exists.
Build order
Build a thin slice that works end to end first, so there is a demo even if later steps slip. The controller comes after the departments because it needs something to build.
